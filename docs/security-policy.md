## 1. Binance API 金鑰建立規範 / API Key Creation Standard

### 1.1 權限範圍(Binance API Management 頁面逐項對照)

| 權限開關 | 設定 | 理由 |
|---|---|---|
| **Enable Reading** | ✅ 開啟 | 讀取餘額、訂單狀態、成交紀錄的基本需求,無此權限機器人無法運作 |
| **Enable Spot & Margin Trading** | ✅ 開啟(僅此項下單權限) | [`scope.md`](./scope.md) 第 3 節已確認 v1 僅現貨,此開關同時涵蓋 spot 下單能力 |
| **Enable Margin Loan, Repay & Transfer**(若帳戶介面顯示為獨立開關) | ❌ 關閉;帳戶本身不建立/不啟用 Margin 帳戶 | Binance 的「Spot & Margin Trading」開關本身不會憑空啟用槓桿——沒有 Margin 帳戶,這個開關實質上只作用於現貨。但若帳戶曾經開過 Margin 功能,務必額外確認借貸/劃轉相關子權限保持關閉,避免現貨策略意外有能力借款加槓桿,牴觸 `scope.md` 第 3 節「現貨無槓桿」的既有決定 |
| **Enable Futures** | ❌ 關閉 | `scope.md` 第 3 節明確「第一版只做現貨,永續合約留待第二階段」;此開關若誤開,等於讓一組本應僅現貨的金鑰同時具備開合約倉位的能力,與既有決策直接矛盾,也放大金鑰外洩時的爆炸半徑(合約有強制平倉/爆倉風險,現貨沒有) |
| **Enable Withdrawals** | ❌ 關閉,且不可逆地作為金鑰建立的第一檢查項 | `scope.md` 第 5 節、`architecture-spec.md` 4.6 節皆已列為前提假設。**這是本文件對「金鑰外洩最大損失上限」唯一有效的結構性控制**:即使金鑰外洩,攻擊者能做的最壞情況是「用你的錢下爛單」,不是「把資產轉走」——第 6 節的 Incident Response 流程整個設計都建立在這個假設成立的前提上,若此開關誤開,第 6 節 IR-1 的風險模型需要整個重新評估 |
| **Enable Internal Transfer / Enable Universal Transfer**(若顯示) | ❌ 關閉 | 同屬廣義的「資產轉移」能力,即使不是提現到外部地址,帳戶內部劃轉(例如轉去一個攻擊者可控的子帳戶)仍是應排除的攻擊面,不在本專案任何功能需求範圍內 |
| **IP access restriction** | ✅ 限制為信任 IP(見 1.2 節) | 見下節討論 |

**建立流程的實作查核點:** 每次建立新金鑰後,建立當下立即用該金鑰呼叫一個只讀端點(如帳戶餘額查詢)與一個提現端點(預期應回傳權限錯誤)手動驗證——不要只看 Binance UI 上勾選了什麼,UI 呈現與實際生效的權限理論上應一致,但用一次實際 API 呼叫驗證「提現確實被拒絕」比只信任畫面勾選框更可靠,成本也很低。

### 1.2 IP 白名單:VPS 環境下的實務作法

**核心張力:** IP 白名單是縮小金鑰攻擊面最有效的單一控制之一(即使金鑰外洩,沒有從白名單 IP 發出的請求也會被 Binance 拒絕),但本專案部署在雲端 VPS([`tech-stack-decision.md`](./tech-stack-decision.md):Docker image、單一 VPS 常駐),VPS 的公網 IP 若是動態或可能因重建/搬遷而改變,白名單反而可能變成「機器人某天突然全部請求被拒絕」的意外停機來源。

**決定:仍然啟用 IP 白名單,但透過基礎設施層面消除「動態 IP」這個前提,而不是因為這個張力就放棄白名單。**

- **前提修正,而非放棄控制:** [`tech-stack-decision.md`](./tech-stack-decision.md) 已確認是單一 VPS 常駐(不是 auto-scaling、不是無伺服器容器平台這類本質上 IP 會隨實例輪替的架構),因此「這台 VPS 有沒有固定 IP」是一個**一次性的基礎設施設定問題**,不是本專案架構本身帶來的必然限制。幾乎所有主流 VPS/雲端供應商都提供固定公網 IP 的選項(常見名稱:Elastic IP / Reserved IP / Floating IP / 靜態 IP),若目前的 VPS 方案預設配發動態 IP,**應在正式接上 live 金鑰之前,先向供應商申請/綁定一個固定 IP**,這是一次性成本,不是持續的維運負擔。
- **Docker 部署不改變這個結論:** 官方 Freqtrade Docker image 跑在該 VPS 上,對外發出的請求仍然使用宿主機的公網出口 IP(除非額外接了會輪替出口 IP 的 NAT gateway/代理服務,本專案的部署架構未使用此類元件),因此「用 Docker 部署」本身不會讓 IP 白名單這件事變得不可行。
- **若真的暫時無法取得固定 IP:** 寧可接受「IP 一旦變動,機器人會因認證失敗而完全停止交易,需要人工更新白名單才能恢復」這個失效模式,也不要為了避免這個麻煩而把金鑰設為不限制 IP。理由:這個失效模式是**安全失效(fail closed)**——機器人停止運作,不會下單,不會虧損,只是不動;而拿掉 IP 白名單換來的是移除一層在金鑰已外洩情境下唯一還能擋住攻擊者的獨立防線。即使提幣已關閉(1.1 節),一個沒有 IP 限制、外洩後可從任何地方呼叫的交易金鑰,仍然能被用來下爛單、操縱你自己帳戶的部位造成實質虧損——IP 白名單是即使提幣已關閉之後,仍然值得保留的縱深防禦層,不是提幣關閉之後就多餘的控制。
- **白名單維護程序:** VPS IP 變更時(供應商維護、機器重建、搬遷),更新流程為:(1) 先在 Binance UI 手動加入新 IP 到白名單(不移除舊 IP),(2) 確認新 IP 下機器人可正常運作,(3) 再移除舊 IP。這個「先加後刪」順序避免在切換空窗期出現金鑰完全無法使用的中間狀態。

### 1.3 金鑰輪替週期

**決定:固定 90 天(一季)為基礎輪替週期,另加事件觸發式立即輪替。**

**基礎週期為何是 90 天,而非更短:**
- 單人專案的輪替流程本身有操作成本(建立新鑰、更新 `secrets-*.json`、部署、驗證),若週期訂得過短(例如 30 天),實務上容易因為「這次先跳過,下次一定做」而形同虛設——**一個會被確實執行的 90 天週期,防護力優於一個名義上更嚴格但常被跳過的 30 天週期**。
- 90 天同時也是第 2.3 節「秘密未進 git 定期驗證程序」的建議週期,兩件事綁在同一個日曆提醒上執行,降低單人專案漏做例行安全工作的機率。

**事件觸發式立即輪替(不等待週期到期,取代週期性理由中的「只是定期做」):**
- 任何懷疑金鑰外洩的情況(見第 6 節 IR-1)——這種情況下輪替本身就是應變流程的一部分,不是「順便」。
- 任何 `.env`/`secrets-*.json` 可能被暴露的操作之後,例如:螢幕分享除錯、把主控台輸出貼給第三方(含 AI 助理、論壇求助)協助排查問題、複製設定檔到另一台機器暫時測試。
- VPS 供應商/實例更換時(此時 IP 白名單本來就需要更新,順勢一併輪替金鑰,是同一次維運操作的自然延伸,不是額外負擔)。
- 首次由 testnet 進入 live(Phase 9 Go/No-Go 通過後):**即使 testnet 階段使用的金鑰從未外洩過,也應該為 live 建立全新金鑰,不重複使用開發/測試期間存在過的任何金鑰**——這是低成本的保險,不依賴「testnet 金鑰應該很安全」這個假設是否成立。
- 任何觸碰過金鑰載入/設定檔處理邏輯的程式碼變更部署後,建議額外執行一次第 2.3 節的驗證程序(不一定需要輪替金鑰本身,但需要重新確認沒有意外把秘密寫進版本控制)。

## 2. 秘密管理規範 / Secrets Management

### 2.1 金鑰存放機制的定案

[`architecture-spec.md`](./architecture-spec.md) 第 7 節已建立結構基礎:`user_data/configs/secrets-testnet.json`/`secrets-live.json` 作為 Freqtrade `--config` 疊加鏈中攜帶機密的檔案,7.3 節另外提出「環境專屬命名 + `FREQTRADE__EXCHANGE__KEY`/`FREQTRADE__EXCHANGE__SECRET` 環境變數覆寫」作為建議方向。本文件在此定案兩者如何分工,避免同一份機密有兩套彼此可能漂移不一致的存放位置:

| 用途 | 機制 | 說明 |
|---|---|---|
| **Freqtrade 實際讀取的機密來源(唯一權威來源)** | `user_data/configs/secrets-testnet.json` / `secrets-live.json`,透過 `--config` 疊加鏈載入 | 沿用 `architecture-spec.md` 7.2 節已定的結構,不重新設計 |
| **Docker 部署時,秘密如何進到容器裡** | 各環境獨立命名的 env file(例如 `deploy/testnet.env`、`deploy/live.env`,**兩者皆需加入 .gitignore**,見 2.2 節),透過 `docker run --env-file` 或 docker-compose `env_file` 注入,對應到 `FREQTRADE__EXCHANGE__KEY`/`FREQTRADE__EXCHANGE__SECRET` 這組 Freqtrade 已確認支援的環境變數覆寫鍵 | 這是 7.3 節「環境專屬命名」建議的落地位置——**檔名本身就區分環境**(`testnet.env` vs `live.env`),不是同一個檔案內用一個布林 flag 切換,結構上延續 7.3 節「設定檔用錯」與「金鑰用錯」兩種故障模式分開防護的精神 |
| **根目錄 `.env`/`.env.example`** | **不再作為交易金鑰的存放位置**,現行 `BINANCE_API_KEY`/`BINANCE_API_SECRET`/`BINANCE_USE_TESTNET` 三個變數予以移除(這正是 `architecture-spec.md` 7.3 節指出的反例:同一組變數 + 一個切換 flag,flag 設反時金鑰仍然「有效」只是打到錯的環境)。`.env.example` 保留給**非交易所機密**(例如 Telegram bot token、chat ID),同樣採環境無關但用途明確的命名,不使用會誘發「共用一組 + flag」模式的命名方式 | 明確結案 `architecture-spec.md` 7.3 節「本文件僅提出目標命名方向,不在此變更 `.env.example` 本身」留給 Phase 5 的待辦 |

**關鍵原則(呼應 architecture-spec 7.3 節「讓設定檔用錯與金鑰用錯是兩個獨立故障模式」):** `secrets-testnet.json`/`secrets-live.json` 與 `deploy/testnet.env`/`deploy/live.env` 的環境對應關係必須完全平行、不交叉——即使兩者理論上攜帶相同的金鑰值,也要各自獨立維護、各自獨立輪替(第 1.3 節),不要為了「省事」讓其中一個去讀另一個的內容再轉發,那樣會讓本應獨立的兩個故障模式重新耦合在一起。

### 2.2 修正 `.gitignore` 的具體缺口

`architecture-spec.md` 2.3 節已明確指出:現行 `.gitignore` 的 `secrets.json` 是精確檔名比對,不會擋到新命名的 `secrets-testnet.json`/`secrets-live.json`。本文件在此定案修正方式,並驗證修正不會誤傷應該被 commit 的範例檔案(`secrets-testnet.example.json`/`secrets-live.example.json`,見 `architecture-spec.md` 2.1 節目錄樹)。

**新增的 `.gitignore` 規則:**

```
# Freqtrade per-environment secrets (Phase 5 fix — glob covers secrets-*.json,
# exact-match `secrets.json` above does not)
user_data/configs/secrets-*.json
!user_data/configs/secrets-*.example.json

# Docker per-environment env files carrying FREQTRADE__EXCHANGE__KEY/SECRET (2.1 節)
deploy/*.env
!deploy/*.example.env
```

**正確性驗證(已用實際 git 倉庫測試,非僅紙上推演):**

1. **若只寫 `secrets-*.json`(不加否定規則)是錯的**——這個較樸素的寫法看似涵蓋了需求,但 `*` 同樣會吃進 `secrets-testnet.example.json`(`secrets-` 開頭、`.json` 結尾,中間的 `testnet.example` 全部落在 `*` 範圍內),導致範例/樣板檔案被一併排除在版本控制之外。這不是理論疑慮:實測建立一個只有 `secrets-*.json` 一行的 `.gitignore`,`git check-ignore` 對 `secrets-testnet.example.json` 回報「已忽略」,確認此寫法會讓範例檔案永遠無法被 commit,而開發者很可能不會注意到——`git status` 根本不會列出這個檔案為 untracked,新加入專案的人也就看不到這個範例可以參考。
2. **加上 `!user_data/configs/secrets-*.example.json` 後,問題解決**——已用實測驗證:`secrets-testnet.json`、`secrets-live.json` 正確被忽略;`secrets-testnet.example.json`、`secrets-live.example.json`、以及同目錄下不相關的 `config-common.json` 皆維持可追蹤/可見狀態,不受影響。git 的否定規則(`!`)之所以能生效,是因為父目錄 `user_data/configs/` 本身沒有被整層排除(現行 `.gitignore` 的 `data/` 規則作用於 `user_data/data/`,不影響 `user_data/configs/`)——若未來有人在 `.gitignore` 加入排除整個 `user_data/` 目錄的規則,這條否定規則會失效(git 的已知限制:父目錄被排除時,子項目的否定規則不會生效),屆時需要同步檢查。
3. **路徑限定為 `user_data/configs/` 而非全倉庫的 `secrets-*.json`**——刻意把規則限定在已知的實際存放路徑,而非讓它對整個 repo 生效。理由是雙向的:限定路徑降低了「未來某個完全無關的 `secrets-report.json` 之類檔案被誤判為機密而永遠無法 commit」的機率,同時只要目錄結構如 `architecture-spec.md` 2.1 節所定不變,限定路徑不會漏掉真正的機密檔案。若未來目錄結構調整,此規則需要同步搬移。

沿用既有 `.env`/`!.env.example` 的否定規則寫法慣例(現行 `.gitignore` 已有此模式),風格上與既有規則一致。

### 2.3 定期驗證秘密未被 commit 的程序

`.gitignore` 只能防止「之後」的 commit 意外收錄機密,不能回頭清除「已經」進了 git 歷史的機密(即使後來刪除該檔案,內容仍留在歷史紀錄中,任何有 clone 權限的人都能挖出來)。本文件要求以下**週期性**(非一次性)驗證程序,與第 1.3 節的金鑰輪替共用同一個 90 天日曆提醒:

1. **確認目前工作目錄沒有應排除卻未被排除的檔案:**
   ```
   git status --porcelain --ignored | grep -E "secrets-(testnet|live)\.json|\.env$"
   ```
   預期應該完全沒有輸出(代表這些檔案要嘛不存在於工作目錄、要嘛已被正確標記為 ignored)。若看到它們出現在非 `!!` (ignored) 開頭的行,代表 `.gitignore` 目前沒有正確涵蓋,需立即修正並視同第 6 節 IR-1 的觸發條件處理(先假設可能已經外洩)。
2. **掃描完整 git 歷史(含已刪除檔案),確認機密檔案從未被真正 commit 過:**
   ```
   git log --all --full-history -- "**/secrets-testnet.json" "**/secrets-live.json" "**/.env" "deploy/*.env"
   ```
   預期輸出應為空。若非空,代表機密檔案曾經被 commit 過(即使現在的 HEAD 已經不含它),必須視為**已外洩**處理(私有 repo 不等於零風險——協作者存取、repo 可視性設定被誤改、CI/CD 執行紀錄外洩、本機曾經 push 到其他 remote/fork 等情境都可能造成暴露),直接進入第 6 節 IR-1 流程,而不是「反正沒人看到就算了」。
3. **掃描 commit 內容本身(而非只看檔名)是否曾意外貼入金鑰字串:** 建議使用開源秘密掃描工具(例如 `gitleaks`、`trufflehog`)對完整歷史掃描一次,例如概念上等同於 `gitleaks detect --source . --log-opts="--all"`——這一步是防「金鑰被複製貼上進了某個看起來無關的檔案」這類 2.2 節的 glob 規則完全防不到的情境(例如貼進一段除錯用的 commit message、貼進一個臨時的 notebook 儲存格)。
4. **額外觸發時機(不等 90 天週期):** 任何一次 commit 觸碰到 `user_data/configs/`、`.env*`、`deploy/`、`.gitignore` 本身、或任何部署腳本之後,建議立即額外跑一次上述第 1、2 步驟(輕量,幾秒鐘可完成),而不是等到下一個 90 天週期——這類變更正是最容易意外納入機密的時刻。

## 3. 日誌脫敏規則 / Log Redaction Rules

### 3.1 絕對不可出現在日誌(含 Telegram 通知)中的欄位

| 類別 | 具體項目 | 說明 |
|---|---|---|
| 金鑰本身 | `BINANCE_API_KEY`、`BINANCE_API_SECRET` 明文值 | 最基本要求 |
| HTTP 標頭 | `X-MBX-APIKEY` 標頭值 | ccxt/Freqtrade 在 `DEBUG` 等級可能完整印出 HTTP 請求標頭,這個標頭直接等同金鑰本身 |
| 簽名請求參數 | 已簽名請求 URL 中的 `signature=` 查詢參數值 | 雖然簽名本身不能反推出 secret,但完整記錄簽名 + 對應請求參數等同留下可被重放分析的敏感軌跡,且往往與其他敏感參數(如帳戶餘額、確切下單量)同一行出現 |
| WebSocket session | `listenKey`(user data stream) | 外洩後可被用來訂閱該帳戶的私有 WebSocket 資料流(訂單/餘額變化即時推播),雖不能下單,但構成資訊洩漏面 |
| Telegram 憑證 | `TELEGRAM_BOT_TOKEN` | 與交易金鑰同等敏感——外洩後攻擊者可能冒充該 bot 對操作者發送偽造訊息(例如偽造的風控告警),或搶先取得原本該只有操作者能看到的部位/餘額推播內容 |
| 原始 HTTP 請求/回應 dump | 任何 `DEBUG` 等級可能輸出的完整 request/response body | 見 3.2 節,這是最主要、最容易被忽略的洩漏管道,因為問題不在單一欄位而在整個記錄等級的預設值 |

### 3.2 機制一(主要防線):正式環境預設一律 `INFO`,不用 `DEBUG`

`architecture-spec.md` 5.2 節已把「預設用 `INFO` 而非 `DEBUG` 等級運行常駐服務」列為建議。本文件將其**升級為硬性規則,而非建議**:

- **testnet 與 live 環境的常駐部署,日誌等級一律固定為 `INFO`,不得設為 `DEBUG`。** 這是最有效的單一控制,因為 ccxt/Freqtrade 的 `DEBUG` 等級之所以危險,不是因為某個特定欄位設計不良,而是它本質上是為了除錯而完整印出 HTTP 層的請求/回應內容(含標頭與簽名查詢字串)——防守這個等級的唯一可靠方式是「不要在正式環境開啟它」,而不是試圖窮舉並過濾 `DEBUG` 輸出裡每一個可能出現機密的位置。
- **若真的需要更高詳細度除錯:** 一律在 **testnet 環境、使用 testnet 專屬金鑰**進行(呼應第 1、2 節 testnet/live 金鑰完全分離的設計),不得為了除錯方便暫時把 live 部署的等級調成 `DEBUG`——這正是「除錯需求」與「金鑰保護」兩個目標唯一不衝突的做法:live 環境永遠不需要為了除錯而承擔額外的洩漏風險,因為同樣的程式邏輯已經可以在 testnet 用低風險的金鑰重現問題。

### 3.3 機制二(次要防線,補漏用):脫敏過濾規則

機制一防的是「預設等級不該記那麼細」,機制二防的是「即使在 `INFO` 等級,程式碼仍可能因為疏失把機密內插進一行原本無害的訊息裡」(例如某個例外訊息、某個 Telegram 通知字串意外組進了完整的請求物件)。所有輸出到日誌檔或 Telegram 的文字,在真正寫出/送出前應經過一層以下樣式的正則遮蔽(概念示意,實作時對應 Python logging 的 `Filter`/`Formatter` 或等價機制,置於 log handler 與 Telegram 送出函式共用的路徑上,而非各自重複實作):

```
(?i)(api[_-]?key["']?\s*[:=]\s*["']?)([A-Za-z0-9]{8,})       →  \1***REDACTED***
(?i)(api[_-]?secret["']?\s*[:=]\s*["']?)([A-Za-z0-9]{8,})    →  \1***REDACTED***
(?i)(x-mbx-apikey:\s*)(\S+)                                    →  \1***REDACTED***
(signature=)([A-Fa-f0-9]{64})                                  →  \1***REDACTED***   # HMAC-SHA256 恆為 64 hex 字元,可精確匹配不誤傷其他參數
(?i)(telegram[_-]?bot[_-]?token["']?\s*[:=]\s*["']?)(\d+:[A-Za-z0-9_-]{30,})  →  \1***REDACTED***
```

**這是防禦縱深的第二層,不是取代機制一**——機制一(不開 `DEBUG`)是主要控制,機制二是假設機制一某處仍有疏漏時的兜底,兩者職責不同,不可只做其中一個就視為完成。

### 3.4 例外處理與 Telegram 告警路徑必須同樣受這層過濾保護

一個容易被忽略的洩漏管道:**未捕捉例外的堆疊追蹤**。ccxt 的 HTTP client 在拋出例外時,例外訊息本身有時會把完整的請求內容(含標頭、查詢字串)字串化進 exception message——若機器人的例外處理邏輯把這段原始例外文字直接轉發進 Telegram 告警(`risk-policy.md` 5.2 節已要求熔斷/異常事件要有即時推播),等於機制一、二都繞過了,機密透過「錯誤通知」這個管道外洩。**要求:任何轉發到 Telegram 或寫入持久化日誌的例外/錯誤文字,必須先經過 3.3 節同一套過濾規則,不能因為是「錯誤處理路徑」而視為特例跳過。**

### 3.5 與部署層的分工(呼應 architecture-spec 5.2)

日誌輪替(rotation)、保存期限維持 `architecture-spec.md` 5.2 節已定的分工:交由部署層(`logrotate` 或 Docker log driver)處理,不在應用層重造。本文件補充兩點:

- **保存期限建議與第 1.3 節、第 2.3 節同步設為 90 天**,三件週期性維運工作共用同一個時間尺度,降低單人專案要記住的「不同東西不同週期」認知負擔。
- **落地的日誌檔案權限應比照機密檔案處理**(非全域可讀),即使已套用 3.3 節脫敏過濾,日誌內容仍包含帳戶層級的交易細節(部位大小、進出場價格、損益),本身就是不該任意暴露的敏感資訊,不是脫敏後就等同公開等級的資料。

## 4. Testnet / Mainnet 啟動時強制環境確認機制 / Startup Environment Confirmation

> 本節是 [`architecture-spec.md`](./architecture-spec.md) 7.1 節明確交棒的主要產出:「Phase 5 之後會在此基礎上再加一層『啟動時強制顯示環境並要求二次確認』的程序性防護」。7.2/7.3 節已經把「目前是哪個環境」在**設定檔結構層級**做到不可能混淆(不同檔名、不同資料庫路徑、不同金鑰變數集合);本節要做到的是把這個結構性事實,在**每一次人為啟動的當下**,清楚攤在操作者眼前並要求主動確認,而不是假設操作者一定會自己記得檢查用了哪個 `--config` 組合。

### 4.1 設計原則

- **單人專案,不過度工程化**(呼應 `architecture-spec.md` 4.5 節對「不建置對抗性防護」的既有立場):真正的風險是操作者自己一時疏忽用錯環境,不是要防範惡意繞過——因此本節設計一個**啟動前檢查腳本 + 打字確認**的組合,而非一整套獨立的看門狗服務或需要額外基礎設施的機制。
- **判斷「目前是哪個環境」不能只信任檔名慣例,要交叉驗證。** 檔名(`config-live.json` vs `config-testnet.json`)是操作者選擇載入哪些檔案的意圖,但意圖可能打錯字、可能疊加了錯誤的組合。真正決定機器人是否會送出真實訂單的,是 Freqtrade 合併後生效設定中的 `dry_run` 布林值。因此檢查腳本的核心邏輯是:
  1. 依實際下達的啟動指令,解析出這次疊加的 `--config` 檔案清單。
  2. 讀出合併後生效設定的 `dry_run` 值,以及實際載入的 `secrets-*.json` 是哪一個(只讀檔名,不讀取/印出內容)。
  3. **交叉核對兩者是否一致**:若載入的是 `secrets-live.json` 但 `dry_run` 卻是 `true`,或載入 `secrets-testnet.json` 但 `dry_run` 是 `false`,視為設定組合矛盾,直接中止啟動並印出具體不一致之處——這正是 `architecture-spec.md` 7.1 節擔心的「設定檔組合搞混」最直接的自動化防線,比只看檔名更能抓到「疊加時漏加/多加了一個檔案」這類實際會發生的操作失誤。

### 4.2 具體機制:啟動前檢查腳本(pre-flight check)

**作為啟動機器人的唯一正式入口**——任何人為啟動(部署、change 後重新上線、冷靜期後恢復)一律先經過這個檢查腳本,不直接下 `freqtrade trade --config ...` 指令(概念示意,非要求具體檔名/實作語言,實作留給後續階段):

1. **印出環境橫幅(banner),内容包含:**
   - 本次疊加的 `--config` 檔案清單(依疊加順序列出檔名,不印內容)
   - 解析出的 `dry_run` 值與 4.1 節交叉核對結果
   - 實際載入的機密檔案**檔名**(例如 `secrets-live.json`),絕不印出其內容或其中任一欄位值——橫幅本身也受第 3 節脫敏規則約束,不能因為是啟動時的一次性輸出就放寬標準
   - 目前部署程式碼的 git commit hash(呼應 `risk-policy.md` 第 7 節「git commit 是正式變更紀錄」的精神,讓操作者能一眼確認現在跑的是不是預期的那個版本)
   - **僅在判定為 live 環境時額外顯示**:從程式碼讀回的關鍵風控數字(`risk_fraction` 上限 1.5%、kill switch 門檻 -15%、單筆/合併名目部位上限 50%/80%)——目的是讓操作者在真正推上 live 之前,用肉眼再確認一次這些數字與 `risk-policy.md` 拍板的數字相符,抓住「部署了一份舊版本或改錯程式碼」這類 4.1 節交叉核對抓不到的情境
2. **若判定環境為 live:要求操作者輸入一段包含當天日期的完整確認語句**,例如:
   ```
   輸入以下文字以繼續(需完全相符,包含今天日期):
   I CONFIRM LIVE TRADING 2026-08-07
   ```
   刻意不用 `[y/N]` 這種單鍵確認——單鍵按鈕容易變成肌肉記憶式的反射動作,失去確認應有的「強迫看一眼、想一下」效果。要求輸入的字串包含當天日期,一方面提高照抄舊指令稿蒙混過關的成本,另一方面順帶讓操作者對照橫幅上的其他資訊(第 1 點)不是敷衍輸入。任何輸入不完全相符,腳本以非零狀態結束,**在此之前完全不會呼叫 `freqtrade trade`**,不留任何副作用。
3. **若判定環境為 testnet:仍然印出完整橫幅(不因為是低風險環境就跳過),但只需要 `[按 Enter 繼續 / Ctrl-C 中止]` 的輕量確認即可。** 兩個環境都印橫幅,是為了避免操作者因為「testnet 從來不用輸入什麼」而養成看到橫幅就反射性略過的習慣,若只有 live 才印,反而讓「有印橫幅」這件事本身變成一個危險訊號被忽略的線索(操作者可能誤以為橫幅不出現才是正常)。testnet 路徑的確認成本刻意壓低,對應「這個環境動用不到真實資金」的風險等級,符合比例原則,不強加與 live 相同的儀式感。

### 4.3 明確否決的替代方案(與理由)

| 被否決的方案 | 否決理由 |
|---|---|
| 用一個 `--yes-i-am-sure` 之類的 CLI 參數取代互動確認 | 這類參數幾乎必然會被寫進啟動腳本、shell alias 或 systemd unit 檔案裡「一勞永逸」地帶上,之後每次啟動實質上都不會再被人看見或思考,完全違背「啟動時強制看見」的目的 |
| 只用終端機顏色(例如 live 用紅色橫幅)標示,不要求任何輸入 | 純視覺提示依賴操作者當下剛好有在注意,沒有強迫互動的成本,容易在疲憊或匆忙時被完全略過 |
| 圖形化介面彈窗確認 | 與 headless VPS/Docker 常駐部署的實際運行環境不符,無謂增加基礎設施需求,不符合單人專案的比例原則 |

### 4.4 與行程監督自動重啟機制的相容性(補上一個容易被忽略的衝突點)

`architecture-spec.md` 6.2 節已確定崩潰後由 systemd(`Restart=on-failure`)或 Docker restart policy(`unless-stopped`/`on-failure`)自動重啟。這與本節「啟動時要求互動輸入」存在明顯的潛在衝突:若 `freqtrade trade` 本身被包在需要互動輸入的腳本裡,一次無人在場的當機自動重啟,要嘛會卡在等待輸入(等同讓自動復原機制失效,造成本不該發生的停機),要嘛若被繞過設計成自動跳過確認,則會讓本節整個防護形同虛設。

**解法:區分「人為決策啟動」與「自動復原重啟」兩種路徑,確認動作只發生在前者:**

- **本節的互動式檢查腳本,執行時機是操作者(重新)安裝/更新 systemd unit 或 docker-compose 設定的當下**——也就是每次操作者要「決定接下來用哪一組 `--config` 組合長期運行」的那個時間點(新部署、環境切換、第 6 節事故後恢復、`risk-policy.md` 第 7 節參數變更後重新部署),而不是每一次行程重啟都重跑一次。
- **systemd unit / docker-compose 檔案本身的啟動指令是靜態的**,只會在操作者手動編輯部署設定時改變——這代表「這次到底要跑哪個環境」這個真正需要人類介入把關的決策點,只發生在操作者主動修改部署設定的時刻,而崩潰後的自動重啟只是**重新執行同一份、已經被人類互動確認過的設定**,並沒有重新做出任何環境選擇,因此不需要、也不應該在自動重啟時重新要求互動輸入。
- 換句話說:本節的確認機制掛在「部署/決定要跑什麼」這個動作上,不是掛在「行程有沒有活著」這個動作上——兩者是不同層級的問題,`architecture-spec.md` 6.2 節處理的是後者,本節處理的是前者,兩者不衝突。

## 5. 訂單參數驗證 / 胖手指防護 / Order Parameter Validation & Fat-Finger Protection

> 本節是防禦縱深的最後一層檢查,**不建立新的風控數字**——所有門檻數字直接取自 [`risk-policy.md`](./risk-policy.md) 已拍板的既有決定(第 0、1、4 節),本節只定義「如何用一個獨立於主要計算路徑的檢查,確保這些既有數字真的被遵守」。

### 5.1 為什麼需要一層獨立的最終檢查

`risk-policy.md` 第 1.4 節已定義部位大小公式 `position_size = (risk_fraction × Equity) / (k × ATR)`,並在第 4.3 節额外訂了獨立於此公式之外的名目部位上限(單筆 ≤50%、合併 ≤80% 權益)作為 `min()` 運算的一部分。**這個 `min()` 邏輯本身理論上已經足夠**——但理論上足夠的公式,與**實作中確實正確執行**的公式是兩回事:若 `custom_stake_amount` 的實作有 bug(例如 `Equity` 讀到一個過期/錯誤的快照、`ATR` 因資料異常讀成一個接近零的值導致公式分母失真),即使公式設計正確,算出來的結果仍可能違反 `risk-policy.md` 的上限。

**核心原則(這一層檢查存在的唯一理由):不能讓同一段可能有 bug 的計算邏輯,同時是「產生結果」與「檢查結果是否合理」的那個邏輯。**

### 5.2 具體設計:獨立來源的硬上限 + 輸入合理性檢查

**在 `custom_stake_amount` 產出 `proposed_stake` 之後、實際送出訂單之前(接線點對應 `confirm_trade_entry` callback,`architecture-spec.md` 3.1 節已確認此 callback 存在且能透過回傳 `False` 否決訂單),加入一層獨立檢查:**

1. **上限值的來源必須與計算 `proposed_stake` 的路徑物理隔離**——即上限值(`risk-policy.md` 4.3 節的單筆 50%/合併 80% 權益、4.2 節的合併 `risk_fraction` 2.5%)寫成獨立宣告的常數,直接對應該文件明訂的數字,不透過任何共用的 Kelly/ATR 計算函式重新推導。這樣一來,即使 `custom_stake_amount` 內的計算邏輯本身有 bug,這層獨立檢查所依據的上限值不會被同一個 bug 污染。
2. **若 `proposed_stake` 超出獨立來源的上限:裁剪(clamp)到上限值,而非直接拒絕整筆交易**——保留「仍然用一個安全的較小部位進場」優於「這個訊號完全被跳過」,呼應 `risk-policy.md` 全篇「暫停新倉」是漸進式反應而非「全有全無」的設計精神。同時**必須觸發告警**(依 `risk-policy.md` 5.2 節已要求的即時推播管道):正常情況下 ATR 公式算出的名目部位,依 `risk-policy.md` 4.3 節自己的算例通常落在約 16.7% 權益,遠低於 50% 的上限——會實際觸及這個上限本身就是一個「上游計算可能有問題」的強訊號,即使这次因為有裁剪而沒有造成實際超額下單,仍值得操作者知道並回頭檢查。
3. **輸入合理性檢查(對公式的輸入做檢查,不只檢查輸出):** `custom_stake_amount` 在計算前應驗證輸入本身是有限、正數、且落在合理範圍——`ATR ≤ 0`、`ATR` 為 `NaN`、`Equity ≤ 0`、`Equity` 為 `NaN`、或 `Equity` 相對上一次讀值出現不合理的單迭代跳動(例如單一迭代內超過 50% 的變化,在本策略每日風險上限 1.5%/合併 2.5% 的既有設計下,這種跳動不該由正常交易損益產生,更可能代表餘額讀取到了過期或錯誤的快照)——任何一項違反,**行為是跳過此次訊號(不下單),而非嘗試用一個猜測值繼續計算**。這是政策層級的要求,具體實作留給 Phase 7/10。

### 5.3 無界重試(unbounded retry)風險

`tech-stack-decision.md` 已確認 ccxt(Freqtrade 內建)已處理交易所呼叫層級的 rate-limit 退避與重試,**這部分不需要、也不應該在我們自己的程式碼再包一層重試**——額外包一層外層重試,在冪等性(`client_order_id` 設計,留給尚未撰寫的 [`execution-spec.md`](./execution-spec.md),Phase 7)沒有完全對齊之前,反而可能造成重複下單,這本身就是一種胖手指風險的變體。

**仍需要我們自己這一層負責的重試邊界:**

- 任何我們自己撰寫的自訂檢查邏輯中,若包含重試(例如 `risk-policy.md` 3.4 節提到的每日損益自訂檢查、本節 5.2 的輸入驗證需要重新查詢一次餘額等情境),**必須有明確的最大重試次數或最大總耗時上限,不得無限重試**,並搭配指數退避 + jitter,避免我們自己的重試行為成為觸發 Binance rate-limit 甚至暫時性 IP 封鎖(HTTP 418/429)的原因——這對第 1.2 節依賴 IP 白名單運作的部署而言,是一個實質的自傷式停機風險,不只是效能考量。
- **重試耗盡後的行為必須是「跳過此次訊號、不下單」,而非「假設一個預設值後繼續」**——例如無法在有限重試內確認目前 `Equity`,正確行為是這次不計算部位大小、不進場,而不是沿用上一次快取的權益值硬算下去。
- 這一節訂的是**政策約束**(任何重試都必須有界、必須 fail closed),具體演算法、次數、退避參數屬於 [`execution-spec.md`](./execution-spec.md)(Phase 7)的職責範圍,本文件只確立這個約束是 Phase 7 設計時必須遵守的前提。

## 6. Incident Response 事故應變流程

> 本節提供兩套**目的不同、首要動作也因此不同**的 runbook,並與 [`architecture-spec.md`](./architecture-spec.md) 4.4 節已定案的 kill switch 人工緊急停止 runbook(`/forceexit all` → `/stop`,風險觸發情境專用)明確區分。單人專案,以下步驟中的「通知」實質上就是「操作者本人依序對自己執行以下檢查」,沒有團隊分工的問題,重點是**步驟順序不能亂**。

### 6.1 三套 runbook 的定位對照

| Runbook | 觸發情境 | 起因是否已知 | 第一步動作 | 為什麼第一步不同 |
|---|---|---|---|---|
| `architecture-spec.md` 4.4 節既有 runbook | `MaxDrawdown`/風控門檻觸發、或操作者主動判斷要按下 kill switch | 已知(回撤門檻本身) | `/forceexit all` → `/stop` | 金鑰本身未受質疑,機器人自己的控制通道(Telegram/REST)可信任,問題在部位曝險,先清空曝險最直接 |
| 本文件 **IR-2**(6.3 節) | 機器人下了一筆非預期的訂單,起因未明 | **未知**——可能是程式 bug、資料異常、或(較低機率)未授權存取 | 同上:`/forceexit all` → `/stop`,**沿用**既有 runbook,再進入調查 | 起因未明時,「先止血、再查因」與風險觸發情境的邏輯一致,不需要另創一套止血動作;調查過程中若發現證據指向未授權存取,立即升級為 IR-1 |
| 本文件 **IR-1**(6.2 節) | 懷疑 API 金鑰外洩/帳戶遭未授權存取 | 已知類別(憑證層級問題),但範圍未知 | **先撤銷金鑰**,而非先用機器人自己的控制通道 | 金鑰本身已不可信任時,不能假設「透過機器人下 `/forceexit`」這個控制通道還有意義——攻擊者可能繞過機器人,直接用同一組金鑰呼叫 API,先撤銷金鑰是唯一能立即切斷所有可能存取路徑(包含機器人自己與攻擊者)的動作,這正是與其餘兩套 runbook 邏輯不同之處 |

### 6.2 IR-1:懷疑 API 金鑰外洩

**判斷觸發:** 出現任一以下情況——`.env`/`secrets-*.json` 可能被意外暴露(截圖、貼給第三方、螢幕分享時可見)、第 2.3 節定期驗證發現機密曾經進過 git 歷史、VPS 出現無法解釋的異常存取跡象、或 6.3 節 IR-2 調查中發現訂單無法對應到任何機器人程式碼路徑。

1. **立即撤銷該金鑰**(Binance UI → API Management → Delete),不等待確認「是否真的外洩」——這是本流程與其他兩套 runbook 最核心的差異(見 6.1 節)。因為提幣權限已依第 1.1 節關閉,撤銷金鑰的下檔風險極低(機器人會開始對所有交易所呼叫回報認證失敗,這是預期且可接受的),但延遲撤銷的下檔風險是攻擊者持續有窗口下單。
2. **金鑰撤銷後,直接登入 Binance 網頁介面**(不透過機器人)檢視懷疑暴露期間的訂單紀錄、成交紀錄、目前掛單——這一步刻意繞過機器人自己的本地 SQLite 交易紀錄與日誌,因為若金鑰確實外洩,攻擊者透過同一組金鑰下的單不必然會被機器人自己的本地帳本記錄到(那套對帳邏輯設計來追蹤機器人自己下的單,見 `architecture-spec.md` 6.2 節前提假設)。
3. **手動於 Binance UI 取消任何無法辨識的掛單**——此時金鑰已撤銷,機器人無法代為執行,必須手動處理。
4. **完全停止機器人行程**(systemd stop / docker stop),避免它在金鑰已撤銷的狀態下持續因認證失敗而反覆重試、洗版日誌與 Telegram 通知,干擾接下來的調查。
5. **在建立新金鑰之前,先釐清外洩途徑**:對照第 2.3 節程序重新檢查 git 歷史、檢查 shell/操作紀錄是否有貼過機密內容、檢查 VPS 本身是否有遭入侵跡象(異常行程、異常 SSH 登入紀錄、異常對外連線)。**若 VPS 本身疑似遭入侵,問題範圍已超出單一金鑰外洩,應視為整台機器不可信,從乾淨映像重建 VPS 後才恢復交易,而不是只換一把金鑰、在同一台可能已受污染的機器上繼續跑**。
6. **確認外洩途徑、且已在可信任的環境後,才依第 1.1 節標準建立新金鑰**——不要在還沒搞清楚怎麼外洩的情況下就急著換新鑰恢復交易,若外洩管道本身還沒堵住(例如仍在用會被監控的機器、仍在用已洩漏的部署腳本),新金鑰同樣會很快再次外洩。
7. **記錄事故**:發現時間、懷疑外洩途徑、採取行動與各自時間戳、UI 檢視發現的訂單紀錄、財務影響(若有)——比照 `risk-policy.md` 第 7.6 節「寫下來」的紀律,這是本專案自己的事故歷史。
8. **恢復交易前,套用 `scope.md` 既有的 ~24 小時冷靜期原則**(即使這不是嚴格意義上的 kill switch 觸發事件,但「調查未完全結束前就急著恢復」屬於同一種需要冷靜期規則防範的衝動決策模式),並且**只能透過第 4 節的啟動確認程序恢復**,不得繞過。

### 6.3 IR-2:機器人下了非預期的訂單

**判斷觸發:** 觀察到一筆自己不記得或不理解為何會發生的訂單/部位,尚不確定原因。

1. **第一步與 `architecture-spec.md` 4.4 節既有 runbook 完全相同:`/forceexit all` → `/stop`**——不重新發明一套止血動作,「非預期訂單」與「風控門檻觸發」在「要不要先停損」這件事上結論相同,4.4 節的 runbook 本來就設計成不論觸發原因為何都安全。
2. **此階段不撤銷金鑰**(與 IR-1 的關鍵差異)——尚未確認是否為未授權存取,保留金鑰可用,才能透過機器人自己的控制通道(Telegram `/status`、`/trades`)取得資訊,也保留了若第 3 步排除異常後直接復原的彈性。
3. **調查根因**,對照以下情境分類:
   - **(a) 策略/程式邏輯 bug** — 檢視觸發該訂單的 `entry`/`exit` 條件與程式碼邏輯是否吻合,是否與近期一次程式碼部署的時間點相關(比對 git log)。
   - **(b) 資料/計算異常** — 檢查第 5.2 節的裁剪機制是否被觸發過(若有觸發,代表上游輸入已經出現過異常,需回頭查為什麼)。
   - **(c) 邏輯正確,只是操作者沒預期到** — 例如一筆完全符合策略設計的 Donchian 突破訊號,只是操作者剛好沒在關注、覺得意外——這不是 bug。
   - **(d) 找不到任何機器人程式碼路徑能解釋這筆訂單**(例如訂單形狀與策略邏輯完全對不上,或機器人程式確認沒有在運行的期間仍出現新訂單)——**這是升級訊號,立即轉入 6.2 節 IR-1 流程(先撤銷金鑰),不要繼續當作單純 bug 排查下去**。
4. **若根因為 (a) 或 (b):** 屬於 `risk-policy.md` 第 7 節定義的「風控參數/程式碼變更」範圍(程式碼修正本身就是一種需要走該流程的變更),須經 git commit(附修改原因與日期)後才可恢復,不得就地熱修(live-patch)。
5. **若根因為 (c):** 不需要程式碼變更,但仍建議記錄下來(避免未來重複花時間調查同一個「其實正常」的行為模式),不需要套用冷靜期。
6. **若根因為 (a)/(b)/(d):** 恢復前套用與 IR-1 相同的冷靜期原則;(d) 的情況需完整走完 6.2 節 IR-1 的其餘步驟(撤銷金鑰、UI 核對、釐清途徑),不能只做 IR-2 這一半。
7. **一律透過第 4 節的啟動確認程序恢復**,不繞過。
